Abstract  The   Vehicle   Parking   Management   System   is   a   full-stack   MERN   web   application   that addresses   the   challenge   of   manual,   inefficient   parking   slot   management.   This   project implements   a   complete   DevOps lifecycle - encompassing containerization with Docker, orchestration   via   Kubernetes,   and   end-to-end   CI/CD   automation   using   Jenkins.   The application enables real-time slot availability checking, booking, and cancellation for multiple vehicle types (Bike, Car, EV, Truck). Automated testing is performed using Jest, with 17 tests across 8 test suites, all passing. Docker images are published to Docker Hub and deployed to a Kubernetes cluster with Horizontal Pod Autoscaling (HPA), Persistent Volume Claims (PVC), and Ingress routing. Jenkins Build #9 achieved a complete pipeline SUCCESS from GitHub   checkout to Kubernetes deployment, demonstrating a production-ready DevOps workflow for a real-world web application.  4. Introduction  4.1 Problem Statement  Traditional parking management systems rely on manual processes - attendants physically checking slots, paper-based booking records, and no real-time visibility into slot availability. This leads to inefficiency, double-booking errors, and poor user experience. The project addresses these issues by building a full-stack MERN application for real-time parking slot management and applying industry-standard DevOps practices to automate its build, test, and deployment processes.

4.2 Objective  The main objectives of this mini project are: •   Automate   the   complete   build,   test,   and   deployment   lifecycle   using   a   Jenkins Declarative CI/CD Pipeline •   Containerize all application services (frontend, backend, MongoDB) using Docker and Docker Compose •   Orchestrate   containers   with   Kubernetes   for   scalability,   persistence,   and ingress-based routing •   Implement   automated   unit   testing   using   Jest   for   both   backend   and   frontend components •   Publish Docker images to Docker Hub for distribution and version control  4.3 Scope  This project covers full-stack MERN application development, Dockerization of all services, Kubernetes   cluster   deployment   (Docker   Desktop),   Jenkins   CI/CD   pipeline   with   GitHub integration, Docker Hub image publishing, and Jest-based automated testing. Out of scope for   this mini project: cloud-hosted Kubernetes (AWS EKS / GKE), production SSL/TLS certificates,   advanced   monitoring   with   Prometheus/Grafana,   and   multi-environment (staging/production) deployments.  5. System Design & Architecture

6.1 Architecture Diagram 6.2 Workflow Description  The system follows a three-tier architecture - Presentation Layer (React), Business Logic Layer (Express.js), and Data Layer (MongoDB) - all containerized and orchestrated with Kubernetes, driven by a Jenkins CI/CD pipeline. •   Step 1: Developer commits and pushes code to the devops branch of the GitHub repository •   Step   2:   Jenkins   detects   the push via SCM polling and triggers the Declarative Pipeline automatically •   Step 3: Checkout Stage - Jenkins pulls the latest code using GitHub credentials •   Step 4: Install Dependencies Stage - npm ci runs for both backend and frontend •   Step 5: Test Stage - Jest executes 8 test suites (17 total tests); pipeline fails fast on test failure •   Step 6: Build Stage - Docker images are built for backend and frontend services •   Step   7:   Push   Stage   -   Images   are   tagged   and   pushed   to   Docker   Hub (saniar2021/parking-backend, saniar2021/parking-frontend) •   Step   8:   Deploy   Stage   -   kubectl   applies   Kubernetes   manifests   (namespace, MongoDB, backend, frontend) •   Step 9: Smoke Tests & Cleanup - health checks run and workspace is cleaned up

Implementation  7.1 Environment Setup  The project was developed and tested on a local machine running Windows with Docker Desktop (which provides both Docker Engine and a local Kubernetes cluster). Prerequisites installed: Node.js (LTS), npm, Docker Desktop with Kubernetes enabled, kubectl (v1.34.1), and Jenkins run as a Docker container on Port 8080.  7.2 Step-by-Step Implementation  7.2.1 Version Control Setup (Git & GitHub)  A GitHub repository was created at Github link. A dedicated devops branch was used for all DevOps-related   configuration   files   (Jenkinsfile,   Dockerfiles,   docker-compose.yml, Kubernetes manifests). A .gitignore was configured to exclude node_modules, .env files, and build artifacts.  7.2.2 CI/CD Pipeline Configuration (Jenkins)  Jenkins 2.555.1 (LTS) was run as a Docker container and accessed at localhost:8080. Three credentials were configured: docker-credentials (Docker Hub), kubeconfig (Secret file for kubectl),   and   github-credentials   (GitHub   PAT).   A   Declarative   Pipeline   job   named 'parking-devops' was created, pointing to the devops branch. The Jenkinsfile defines 8 stages:  pipeline   {  agent   any  environment   {   DOCKER_CREDENTIALS_ID   =   'docker-credentials'   }  stages   {  stage('Checkout')   {   steps   {   git   branch:   'devops',   credentialsId: 'github-credentials',   url:   '...'   }   }  stage('Install   Dependencies')   {   steps   {   sh   'cd   backend   &&   npm   ci';   sh 'cd   frontend   &&   npm   ci'   }   }  stage('Run   Tests')   {   steps   {   sh   'cd   backend   &&   npm   run   test';   sh   'cd frontend   &&   npm   run   test'   }   }  stage('Build   Docker   Images')   {   steps   {   sh   'docker   compose   build'   }   }  stage('Push   to   Docker   Hub')   {   steps   {   withCredentials([...])   {   sh 'docker   push   ...'   }   }   }  stage('Deploy   to   Kubernetes')   {   steps   {   withCredentials([...])   {   sh 'kubectl   apply   -f   k8s/'   }   }   }  }  }





7.2.3 Containerization with Docker  Three services are containerized using Docker Compose: parking-frontend (React Vite, Port 3000), parking-backend (Node.js API, Port 5000), and parking-mongodb (MongoDB, Port 27017 with named volume for data persistence). Key Docker commands:  docker   compose   up   -d   #   Start   all   services

docker   compose   exec   backend   npm   run   test   #   Run   tests   in   container  docker   tag   ...   /parking-backend:latest   #   Tag   image docker   push   saniar2021/parking-backend:latest   #   Push   to   Docker   Hub

7.2.4 Kubernetes Orchestration  Kubernetes   manifests   were   organized   under   k8s/   (namespace,   mongodb/,   backend/, frontend/). Key resources deployed to the parking-system namespace: •   Deployments: parking-frontend (2 replicas), parking-backend (2 replicas), mongodb (1 replica) •   Services: ClusterIP services for frontend (Port 80), backend (Port 5000), mongodb (Port 27017) •   Ingress: parking-ingress routing parking.example.com to frontend on Port 80 •   HPA: parking-backend-hpa - min 2, max 5 replicas, CPU threshold 70% •   PVC: mongodb-pvc - 1Gi Bound volume for MongoDB data persistence •   ConfigMap & Secret: backend-config for environment variables, mongodb-secret for credentials  kubectl version --client kubectl config current-context kubectl cluster-info Apply the Manifests From the project root: kubectl apply -f k8s/namespace.yaml kubectl apply -f k8s/mongodb/

Challenges Faced & Learnings  9.1 Challenges Faced  •   Challenge 1: Jenkins pipeline failures (#5–#8) - Early builds failed due to incorrect Docker credential binding in the Jenkinsfile and missing npm ci step. Resolution: Corrected withCredentials syntax and added separate Install Dependencies stage before the Test stage. •   Challenge   2: Kubernetes HPA showing <unknown> for CPU targets - The HPA reported TARGETS cpu: <unknown>/70% because the Kubernetes metrics-server was not installed in Docker Desktop. Resolution: Acknowledged as a known Docker Desktop limitation; HPA configuration was still validated structurally. Min/max replicas (2/5) were confirmed. •   Challenge   3:   MongoDB   connection   in   Docker   Compose   vs   Kubernetes   -   The backend uses different MongoDB URIs in Docker Compose (mongodb:27017) vs

Kubernetes   (mongodb.parking-system.svc.cluster.local).   Resolution:   Used Kubernetes   ConfigMap   (backend-config)   to   inject   the   correct   MONGO_URI   per environment, keeping the application code unchanged. •   Challenge 4: Docker image tagging for Jenkins push stage - Jenkins could not push images because they were built with docker compose which uses a different naming convention than expected by Docker Hub. Resolution: Added explicit docker tag commands in the Jenkinsfile Push stage to rename images before pushing.  9.2 Key Learnings  •   Hands-on experience with end-to-end Jenkins Declarative Pipeline setup, credential management, and SCM integration •   Practical understanding of Docker multi-service orchestration using Docker Compose and image lifecycle (build → tag → push) •   Real-world Kubernetes deployment including namespaces, deployments, services, ingress, HPA, PVC, ConfigMaps, and Secrets •   Jest unit testing strategies for both Node.js backend (mocking Mongoose models) and React frontend (component rendering tests) •   Importance of fail-fast CI pipelines - running tests before build and deploy stages prevents broken images from reaching the registry  10.
